# SupportLens AI — Decision Log

This log records non-obvious engineering and evaluation decisions made during development.

## 1. Brand selection — AppleSupport

**Decision:** Use AppleSupport as the target brand.

**Why:** The dataset contains a large volume of AppleSupport interactions covering a broad but coherent support domain. This provides enough historical examples for retrieval while keeping the prototype focused.

---

## 2. Primary-problem intent definition

**Decision:** Assign one intent based on the customer's primary support problem.

**Why:** Customer messages frequently mention products, features, and secondary symptoms together. Classifying every keyword would create noisy labels and make evaluation ambiguous.

---

## 3. Device mentions are not automatically hardware intents

**Decision:** Mentioning "iPhone", "iPad", or another Apple device does not imply `HARDWARE_DEVICE`.

**Why:** Device names are often merely context. For example, an iPhone battery complaint should be classified as `BATTERY_POWER`, not hardware.

---

## 4. Use `OTHER` as an explicit fallback

**Decision:** Keep `OTHER` in the final intent taxonomy.

**Why:** Real support traffic contains ambiguous, context-poor, out-of-scope, and non-problem messages. A production-like support agent needs an escape hatch rather than forcing every message into a known category.

---

## 5. Weak labels are only a bootstrap mechanism

**Decision:** Use heuristic rules to create high-confidence training labels, but do not treat them as ground truth.

**Why:** The raw Twitter dataset does not provide the required support-intent labels. Weak supervision allows a lightweight classifier to be trained without manual annotation of the entire dataset.

**Consequence:** An independent manually labelled Golden Set is required to measure real generalization.

---

## 6. Lock the Golden Set

**Decision:** Freeze the 196-example Golden Set before evaluating the classifier.

**Why:** Changing labels or examples based on model predictions would turn the test set into a tuning set and make the reported performance unreliable.

---

## 7. Prevent Golden Set leakage

**Decision:** Exclude Golden Set customer/support examples from the historical training corpus used by the pipeline.

**Why:** A historical retrieval system can otherwise retrieve the exact evaluation example, producing artificially strong evidence.

---

## 8. TF-IDF for retrieval

**Decision:** Use TF-IDF with unigrams and bigrams for historical retrieval.

**Why:** It is lightweight, deterministic, interpretable, requires no paid API, and runs comfortably on the available hardware.

**Trade-off:** Lexical retrieval misses semantic similarity and vocabulary variation.

---

## 9. Retrieve Top-5 rather than trusting Top-1

**Decision:** Retrieve five historical cases instead of using only the highest-ranked case.

**Why:** The highest lexical similarity does not always correspond to the best support precedent. Multiple examples provide a stronger evidence base and allow repeated resolution actions to be identified.

---

## 10. Aggregate resolution actions

**Decision:** Extract resolution actions from each retrieved historical reply and aggregate them across the Top-5 cases.

**Why:** A single historical reply may be noisy or overly specific. Repeated actions across multiple cases provide stronger evidence.

---

## 11. Deterministic response drafting

**Decision:** Generate the final draft using deterministic templates rather than an LLM.

**Why:** The response should be reproducible, explainable, and grounded in observed historical actions. It also keeps the core system usable without paid API calls.

**Trade-off:** The generated language is less flexible than an LLM-generated response.

---

## 12. Conservative escalation policy

**Decision:** Escalate when intent confidence is low, intent is `OTHER`, historical evidence is insufficient, or no strongly supported action exists.

**Why:** In customer support, unsupported automated advice can be worse than asking a human to review the case.

---

## 13. Do not treat weak-label validation as the headline metric

**Decision:** Report the independent Golden Set performance as the meaningful classifier evaluation.

**Why:** The classifier achieved 94.73% accuracy on a weak-label validation split, but those labels were generated by the same heuristic system used for training. The independent Golden Set produced 41.33% accuracy.

**Conclusion:** The 94.73% figure measures agreement with the weak-labeling process, not real-world intent accuracy.

---

## 14. Treat retrieval usefulness separately from retrieval accuracy

**Decision:** Report human-labelled retrieval relevance rather than calling similarity scores "retrieval accuracy".

**Why:** TF-IDF similarity measures lexical overlap. A low-similarity result can still be semantically useful, while a high-similarity result can be irrelevant.

**Headline:** 81% of reviewed queries had at least one useful historical case in the Top-5.

**Important qualification:** Only 34% had at least one directly relevant case.

---

## 15. Keep the core evaluation API-free

**Decision:** Do not make the LLM judge part of the default evaluation harness.

**Why:** The main evaluation should be reproducible without an external API, account, or quota. The Gemini judge is retained as a secondary pilot because API availability and free-tier quotas can vary.

**Consequence:** The LLM judge result is explicitly reported as a small pilot rather than a robust benchmark.
